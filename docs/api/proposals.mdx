Treasury payout proposals are exposed through the proposal router and vault proposal routes in the backend.

## List Proposals

```http
GET /api?status=pending
```

Returns proposal records, optionally filtered by status.

## List Vault Proposals

```http
GET /api/vaults/:vaultId/proposals
```

Returns proposals for a specific vault.

<Warning>
  These paths have no `proposals` segment. The proposal router is mounted at `/api` and
  defines bare `/:id` routes, so a proposal is addressed as `/api/<uuid>` — not
  `/api/proposals/<uuid>`, which returns 404.

  The same mounting shadows other handlers at `/api`, which is why `GET /api` returns the
  proposal list rather than an API index. Use [`GET /api/status`](/api/public-endpoints)
  to read service and network information.
</Warning>

## Get Proposal

```http
GET /api/:id
```

Returns a single proposal.

## Create Off-Chain Proposal Record

```http
POST /api/vaults/:vaultId/proposals
x-user-address: bchtest:q...
```

Creates the proposal record before the on-chain proposal state is funded.

## Create On-Chain Proposal State

```http
POST /api/:id/create-onchain
POST /api/:id/confirm-create
```

These routes build and confirm the proposal covenant funding flow.

## Approvals

```http
POST /api/:id/approve-onchain
POST /api/:id/confirm-approval
```

These routes collect proposal approval state on-chain.

## Execute Treasury Payout

```http
POST /api/proposals/:id/execute
POST /api/proposals/:id/execute-signature
```

Both need a wallet sign-in. The first call starts a signing session for two of the vault's signers and returns the payout transaction; later calls by either signer return the same session.

Each signer signs that transaction in their wallet and posts it to `execute-signature` with the `sessionId`. A wallet fills every signature slot with its own signature, so neither copy is valid on its own. When the second copy arrives, the backend takes each slot's signature from the copy signed by that slot's key, broadcasts the combined transaction once, and marks the proposal executed. If the network rejects it, the session is closed (`EXECUTION_BROADCAST_FAILED`, retryable) and the signers start a new one.

## Abandon a Pending Request

```http
DELETE /api/proposals/:id
```

Creator only, with a wallet sign-in. Removes a pending request that never got its on-chain create or any approval, for example after the wallet signature was declined. Refused while coins sit at the request's covenant.

## Low-Level Broadcast

```http
POST /api/broadcast
```

Used by the proposal execution flow when raw transaction broadcast control is needed.

## Scope

These routes document the current treasury proposal implementation that the app uses today.
